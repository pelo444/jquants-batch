# 需給3階層 Web画面（`/demand`）の仕様

`queries/sql/demand_*.sql` の3階層をブラウザで見るための画面。
**運用の手引き（何を見るか・どう読むか）は `docs/DEMAND_SIGNAL_RUNBOOK.md`。**
こちらは「画面として何を約束しているか」と「触るときにどこを壊しやすいか」を書く。

関連: `docs/PROJECT.md` 9章（分析SQLの決めごと）・10.2（Webアプリ）

---

## 0. この画面の約束（変えないこと）

1. **`SIGNAL_SCORE` は買いシグナルではない。** 画面では「確認順」と呼び、
   大きいほど良いという色付けをしない。需給5指標の予測力は10年分で検証済みで、
   いずれも先行リターンの方向を予測できなかった（`demand_signal_backtest.sql`）。
   さらに手元のデータは上昇相場10年分しかなく、上昇依存の手法は反証できない。
2. **NULL と 0 を区別する。** 値が無いセルは 0 でも空白でもなく `—` で出し、
   `title` に「なぜ無いのか」を持たせる。**列ごとに理由が違う**（`demand.js` の `NA_NOTE`）。
   グラフでは欠測を 0 でプロットせず線を切る。
3. **「疑う列」を点灯より目立たせる。** 枠付きのチップにして点灯の**左**に置く。
   列の並びが、そのまま手引き3章の読む順番（① 疑う → ② 点灯 → ③〜⑥ 材料）になっている。
4. **大量保有は向きを必ず見せる。** `LVS_RECENT_SUMMARY` を折りたたまず、
   本文行の下に全文を出す。退出報告でも点灯するので、これを読まずに確認順だけで
   判断すると向きを取り違える。
5. **しきい値を文言に書かない。** `params` を変えた瞬間に嘘になる。
   ラベルは閾値非依存（「空売り残高の増加」であって「空売り残+1.5pt」ではない）にし、
   実際の値はフッターに1箇所だけ出す。
6. **鮮度を常に見せる。** シグナルは最新値で判定するので、どれか1つでも取込が
   止まっていると静かに誤判定する。鮮度バーはタブの外・画面上部に固定で置く。
7. **較正クエリ（05〜11）は画面に出さない。** 全期間の分位を使っていて、その時点では
   知り得ない情報を含むため、日々の判断に混ぜない。出すのは「最後に較正した日」と
   「いま使っているしきい値」だけ。

## 1. ファイル構成

| ファイル | 役割 |
|---|---|
| `src/web/demandQuery.js` | 3階層のSQLとしきい値（`PARAMS`）。**しきい値の唯一の定義場所** |
| `src/web/server.js` | `/demand` と `/api/demand/*` のルーティング・キャッシュ・入力検証 |
| `src/web/public/demand.html` | 画面の骨格。但し書き（lede）はここに書いてある |
| `src/web/public/demand.js` | 列定義と描画。`NA_NOTE` と `doubtChips()` がこの画面の心臓部 |
| `src/web/public/demandChart.js` | 依存ライブラリなしのSVG折れ線。**欠測を 0 で描かない**ための `mode` を持つ |
| `src/web/public/demand.css` | 追加スタイル。系列色はスロット1〜4を固定順で使い、循環させない |

`webQuery.js`（騰落率一覧）とは別ファイルにした。読むテーブルも列の意味も共有しないため、
同じファイルに置くと `PARAMS` の作用範囲が曖昧になる。

## 2. API

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/demand` | 画面本体（`public/demand.html`） |
| GET | `/api/demand/meta` | しきい値・較正日・SECTION一覧・ウォッチリスト |
| GET | `/api/demand/freshness` | 7データの最新日と遅れ日数 |
| GET | `/api/demand/macro` | 第一階層。`section`・`weeks` |
| GET | `/api/demand/watchlist` | 第二階層の需給シート |
| GET | `/api/demand/detail` | 銘柄詳細。`code`・`weeks`（時系列・現在の大量保有者・提出履歴） |
| GET | `/api/demand/pseudo-float` | 疑似浮動株比率（近似） |
| GET | `/api/demand/signals` | 第三階層。ウォッチ銘柄 |
| GET | `/api/demand/signals/all` | 第三階層。全銘柄（**重い**。画面のボタンからのみ） |
| GET | `/api/demand/supplementary` | 補助シグナル（days to cover 等） |

列名は Oracle の大文字スネークを lowerCamelCase に機械変換して返す
（`SHORT_RATIO_PCT` → `shortRatioPct`）。変換は `demandQuery.js` の `toCamel()` の1箇所。

キャッシュは通常5分、`/api/demand/signals/all` だけ30分。日次バッチ直後に古い値が
見えることがある。画面右上の「再読み込み」はクライアント側のキャッシュを捨てるだけで、
サーバ側のキャッシュは切れるまで残る。

## 3. 表示層の規約（ここを潰すと3階層の意味が消える）

| 見え方 | 画面での出し方 |
|---|---|
| `SHORT_RATIO_PCT` が NULL | `—` ＋ 「0.5%以上の報告が無い」という title。**空売りゼロではない** |
| `SHORT_RATIO_PCT` が 0.00 | 値 ＋ `報告終了` または `古い報告のみ` バッジ。どちらも残高ゼロではない |
| `SHORT_STALE_CNT` > 0 | 「疑う列」に `失効扱いの空売り報告 n件`。合計は過小かもしれない |
| 空売りのグラフ | **線**（`mode: 'line'`）。2026-09-16 に報告者ごとの持ち越し合計(ddl/21)に変えたので週ごとに連続する。以前の「点のみ」は、その週に報告した人の分しか無かったため |
| 信用残が NULL の週 | グラフは線を切る。表は `—` ＋「JPXが公表していない」という title |
| `LVS_GRP_CNT = 0` | `0` ＋ バッジ。書類が無ければ「この5年で動きなし」、書類があって5%以上が0件なら「全員退出」 |
| `LVS_TOTAL_PCT` が空 | 保有Gが0なら `—`。割合の記載が無い書類は `LVS_GRP_CNT_NORATIO` に件数が出る |
| `LVS_RECENT_SUMMARY` | 本文行の下に全文。方向（新規/退出/買い増し/売り減らし/割合なし）を色と文言の両方で出す |
| `SIGNAL_SCORE` | 列名は「確認順」。`td.rank` は値の大小で色を変えない |
| 疑う列6つ | 枠付きチップ。色だけに意味を運ばせず、必ず `⚠` と文言を添える |

## 4. 既知の制限

- **銘柄詳細の終値は分割調整していない。** 元にしている第二階層3（週次時系列）が
  生の `CLOSE_PRICE` を返すため。分割のあった週はグラフの注記に週を列挙して、
  水準が飛ぶ場所が分かるようにしてある。調整するなら `fetchCodeTimeseries()` に
  `PROJECT.md` 9章(1) の累積調整係数を入れること（`/chart` 側は調整済み）。
- **`MARGIN_SEASON_WARN` は第三階層・補助シグナルにしか無い。** 第一階層の信用倍率は
  週の行から機械的に判定できてしまうが、SQL側（申込日基準）と別の判定を画面で作ると
  階層間で読み方が食い違う。画面では但し書きと列の title で注意を出すに留めている。
- **認証は未実装**（`README.md` の「認証を組み込むとき」を参照）。
- 全銘柄版は大量保有の全期間スナップショットを作らない。点灯した銘柄の
  「いま誰が何%持っているか」はウォッチリストタブの銘柄詳細で見る。

## 5. 触るときの注意

- **しきい値は `demandQuery.js` の `PARAMS` だけに書く。** SQL文字列にも列ラベルにも
  数値を書かない。`queries/sql/demand_*.sql` の `params` CTE と二重管理になるので、
  動かしたら `node scripts/check-demand-params.js` でずれていないことを確かめる。
- **新しい列を足したら `NA_NOTE` にその列の「無い理由」を足す。** 理由の無い `—` は
  「データが無い」としか言えず、この画面がやろうとしていることの逆になる。
- **階層をまたいで同じテーブルを読むときは、既存SQLと突き合わせる工程を必ず入れる。**
  同じテーブルを同じ意味で読むのだから、読み方が食い違っていること自体がバグ
  （2026-09-14 に第三階層を第二階層へ揃えたときの教訓。9件出た）。
